Operator-sdk: privilege escalation due to incorrect permissions of /etc/passwd

  • Description de la vulnérabilité :

    Early versions of Operator-SDK provided an insecure method to allow operator containers to run in environments that used a random UID. Operator-SDK before 0.15.2 provided a script, user_setup, which modifies the permissions of the /etc/passwd file to 664 during build time. Developers who used Operator-SDK before 0.15.2 to scaffold their operator may still be impacted by this if the insecure user_setup script is still being used to build new container images. In affected images, the /etc/passwd file is created during build time with group-writable permissions and a group ownership of root (gid=0). An attacker who can execute commands within an affected container, even as a non-root user, may be able to leverage their membership in the root group to modify the /etc/passwd file. This could allow the attacker to add a new user with any arbitrary UID, including UID 0, leading to full root privileges within the container.

      • Métriques de base :
        • Exploitabilité :
          • Vecteur d'attaque : Local (AV: L) - Score : 0,55

            La vulnérabilité n’est exploitable que par un attaquant ayant un accès physique ou logique au système cible, ce qui exclut une exploitation à distance via un réseau.

            • Accès requis au système cible : l’attaquant doit disposer d’un accès au système vulnérable. Cet accès peut prendre plusieurs formes :
              • accès logique : l’attaquant possède des identifiants valides et peut se connecter localement au système (par exemple, via une session shell, une session de bureau à distance, ou une interface de ligne de commande). Cela inclut aussi le cas où l’attaquant peut exécuter des commandes ou du code sur le système par le biais d’une session utilisateur existante (par exemple, via celle d’un utilisateur qui ouvre un fichier malveillant).
              • accès physique : l’attaquant a un accès physique au système et peut interagir avec lui directement (par exemple, via un clavier, un port USB, ou en redémarrant le système avec un support externe).
            • Non exploitable via le réseau : la vulnérabilité ne peut pas être exploitée en envoyant simplement des paquets réseau depuis une machine distante. L’attaquant doit d’abord franchir les défenses réseau pour obtenir un accès local ou être physiquement présent.
            • Exemples de scénarios :
              • exécution par un utilisateur local d’un programme malveillant pour élever ses privilèges.
              • exploitation par un attaquant qui a obtenu un accès shell sur le système (par exemple, via une autre vulnérabilité ou des identifiants volés) d’une vulnérabilité locale pour obtenir des droits d’administrateur.
              • branchement par un utilisateur d’une clé USB infectée sur un ordinateur non verrouillé.
            • Interaction utilisateur : dans certains cas, l’exploitation de la vulnérabilité peut nécessiter une interaction avec un utilisateur légitime (qui va, par exemple, ouvrir un fichier malveillant ou exécuter une commande spécifique). Cependant, l’exploitation se produit toujours dans le contexte du système local.

          • Complexité d'attaque : Élevée (AC: H) - Score : 0,44

            Une attaque réussie dépend de conditions indépendantes de la volonté de l’attaquant. C’est-à-dire qu’une attaque réussie ne peut pas être réalisée à volonté, mais exige que l’attaquant investisse un effort mesurable dans la préparation ou l’exécution contre le composant vulnérable avant qu’une attaque réussie puisse être attendue. Par exemple, une attaque réussie peut dépendre du dépassement par un attaquant de l’une des conditions suivantes :

            • L’attaquant doit recueillir des connaissances sur l’environnement dans lequel se trouve la cible/le composant vulnérable. Par exemple, une exigence de recueillir des détails sur les paramètres de configuration de la cible, les numéros de séquence ou les secrets partagés.
            • L’attaquant doit préparer l’environnement cible pour améliorer la fiabilité de l’exploitation. Par exemple, l’exploitation répétée pour gagner une condition de concurrence ou le dépassement de techniques avancées d’atténuation de l’exploitation.
            • L’attaquant doit s’injecter dans le chemin de réseau logique entre la cible et la ressource demandée par la victime afin de lire et/ou de modifier les communications réseau (par exemple, une attaque de l’homme du milieu).
          • Privilèges requis : Élevés (PR: H) - Score : 0,27

            L’attaquant a besoin de privilèges qui fournissent un contrôle important (par exemple, administratif) sur le composant vulnérable, ce qui permet d’accéder aux paramètres et aux fichiers à l’échelle du composant.

          • Interaction utilisateur : Aucune (UI: N) - Score : 0,85

            Le système vulnérable peut être exploité sans interaction avec un utilisateur.

        • Portée : Non changée (S: U)

          Une vulnérabilité exploitée ne peut affecter que les ressources gérées par la même autorité de sécurité. Dans ce cas, le composant vulnérable et le composant touché sont le même, ou les deux sont gérés par la même autorité de sécurité.

        • Impacts :
          • Confidentialité : Faible (C: L) - Score : 0,22

            Il y a une certaine perte de confidentialité. L’accès à certaines informations restreintes est obtenu, mais l’attaquant n’a aucun contrôle sur les informations obtenues, ou la quantité ou le type de perte est limité. La divulgation d’informations n’entraîne pas de perte directe et grave pour le composant touché.

          • Intégrité : Élevé (I: H) - Score : 0,56

            Il y a une perte totale d’intégrité ou une perte complète de protection. Par exemple, l’attaquant est en mesure de modifier tous les fichiers protégés par le composant touché. Sinon, seuls certains fichiers peuvent être modifiés, mais une modification malveillante présenterait une conséquence directe et grave pour le composant touché.

          • Disponibilité : Faible (A: L) - Score : 0,22

            Le rendement est réduit ou il y a des interruptions dans la disponibilité des ressources. Même si l’exploitation répétée de la vulnérabilité est possible, l’attaquant n’a pas la possibilité de refuser complètement le service aux utilisateurs légitimes. Les ressources du composant touché sont soit partiellement disponibles en tout temps, soit entièrement disponibles seulement une partie du temps, mais dans l’ensemble, il n’y a aucune conséquence directe et grave pour le composant touché.
