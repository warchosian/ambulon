1. Principes Généraux

✅ Règle #1 : Privilégier la Complexité

TOUJOURS préférer les structures complexes aux structures simples.

❌ Mauvais exemple (simplicité + notes)

rectangle "Level 1" as level1

note right of level1
  <b>Level 2</b>
  • Item 1
  • Item 2

  <b>Level 3</b>
  • Détail 1
  • Détail 2
end note

rectangle "Level 1" as level1

note right of level1
  <b>Level 2</b>
  • Item 1
  • Item 2

  <b>Level 3</b>
  • Détail 1
  • Détail 2
end note
Pourquoi : L'utilisation de notes peut masquer la structure réelle du diagramme et le rendre moins détaillé.

✅ Bon exemple (structure complexe)

rectangle "Level 1" {
  rectangle "Level 2" {
    rectangle "Level 3" {
      - Item 1
      - Item 2
    }
  }
}

rectangle "Level 1" {
  rectangle "Level 2" {
    rectangle "Level 3" {
      - Item 1
      - Item 2
    }
  }
}
Pourquoi : Les structures imbriquées reflètent mieux la complexité du système.

✅ Règle #2 : Utiliser des Alias Courts

TOUJOURS définir des alias simples pour les éléments.

❌ Mauvais exemple (noms complexes avec \n)

rectangle "1. Arguments CLI\n(Priorité MAXIMALE)" #FF6B6B {
}

note bottom of "1. Arguments CLI\n(Priorité MAXIMALE)"
  Contenu de la note
end note

rectangle "1. Arguments CLI\n(Priorité MAXIMALE)" #FF6B6B {
}

note bottom of "1. Arguments CLI\n(Priorité MAXIMALE)"
  Contenu de la note
end note
Pourquoi : Les caractères spéciaux (\n, :, etc.) dans les identifiants causent des erreurs de parsing.

✅ Bon exemple (alias simple)

rectangle "1. Arguments CLI" #FF6B6B as cli

note bottom of cli
  <b>Priorité MAXIMALE</b>
  Contenu de la note
end note

rectangle "1. Arguments CLI" #FF6B6B as cli

note bottom of cli
  <b>Priorité MAXIMALE</b>
  Contenu de la note
end note
Pourquoi : L'utilisation d'alias simples et courts rend le code plus lisible et évite les erreurs de référence.

✅ Règle #3 : Éviter les Caractères Spéciaux dans les Noms

Liste des caractères à éviter dans les identifiants :
  • : (deux-points) - interprété comme séparateur de stéréotype
  • \n (newline) - cause des erreurs de référence
  • * (astérisque) - conflit avec le markdown PlantUML
  • ** (double astérisque) - conflit avec le bold dans mindmaps

❌ Mauvais exemple

object "feat:" {
  Impact = MINOR
}

object "feat:" {
  Impact = MINOR
}
Pourquoi : L'utilisation de : dans le nom de l'objet est interprétée comme un séparateur de stéréotype et peut causer des erreurs.

✅ Bon exemple

object feat {
  Type = "feat:"
  Impact = MINOR
}

object feat {
  Type = "feat:"
  Impact = MINOR
}
Pourquoi : Le nom de l'objet est un identifiant simple, et le type est défini comme un attribut, ce qui est la syntaxe correcte.

2. Rectangles et Composants

✅ Règle #4 : Limiter le Nesting à 1 Niveau Maximum

NE JAMAIS imbriquer plus de 2 niveaux de rectangles.

❌ Mauvais exemple (3 niveaux de nesting)

rectangle "Niveau 1" {
  rectangle "Niveau 2" {
    rectangle "Niveau 3" {
      Contenu
    }
  }
}

rectangle "Niveau 1" {
  rectangle "Niveau 2" {
    rectangle "Niveau 3" {
      Contenu
    }
  }
}
Pourquoi : Le parser PlantUML a des limites de profondeur pour les nested structures.

✅ Bon exemple (1 niveau + notes)

rectangle "Niveau 1" #LIGHTBLUE as main

note right of main
  <b>Niveau 2:</b>
  • Contenu A
  • Contenu B

  <b>Niveau 3:</b>
  • Détail 1
  • Détail 2
end note

rectangle "Niveau 1" #LIGHTBLUE as main

note right of main
  <b>Niveau 2:</b>
  • Contenu A
  • Contenu B

  <b>Niveau 3:</b>
  • Détail 1
  • Détail 2
end note
Pourquoi : L'utilisation de notes pour représenter les niveaux inférieurs évite les erreurs de parsing et améliore la lisibilité.

✅ Règle #5 : Utiliser les Listes à Tirets dans les Rectangles Imbriqués

TOUJOURS privilégier les listes à tirets dans les rectangles imbriqués pour une meilleure lisibilité.

❌ Mauvais exemple (utiliser des notes)

rectangle "Container" #LIGHTBLUE as container

note right of container
  <b>Actions:</b>
  • Action 1
  • Action 2
  • Action 3
end note

rectangle "Container" #LIGHTBLUE as container

note right of container
  <b>Actions:</b>
  • Action 1
  • Action 2
  • Action 3
end note
Pourquoi : L'utilisation de notes pour de courtes listes peut être verbeuse et moins directe.

✅ Bon exemple

rectangle "Container" {
  rectangle "Actions" {
    - Action 1
    - Action 2
    - Action 3
  }
}

rectangle "Container" {
  rectangle "Actions" {
    - Action 1
    - Action 2
    - Action 3
  }
}
Pourquoi : C'est une syntaxe plus compacte et lisible pour les listes simples.

✅ Règle #6 : Pas de Contenu Indenté (YAML/JSON) dans les Rectangles

NE JAMAIS mettre du YAML, JSON ou code indenté dans les rectangles.

❌ Mauvais exemple

rectangle "Config" {
  config/piag.yaml:
    timeout: 120
    retries: 3
}

rectangle "Config" {
  config/piag.yaml:
    timeout: 120
    retries: 3
}
Pourquoi : L'indentation est interprétée incorrectement par le parser PlantUML.

✅ Bon exemple (utiliser des notes)

rectangle "Config" #LIGHTYELLOW as config

note right of config
  <b>config/piag.yaml:</b>
  timeout: 120
  retries: 3
end note

rectangle "Config" #LIGHTYELLOW as config

note right of config
  <b>config/piag.yaml:</b>
  timeout: 120
  retries: 3
end note
Pourquoi : Les notes préservent le formatage du texte pré-formaté et sont le conteneur approprié pour des extraits de code ou de configuration.

3. Diagrammes d'Objets

✅ Règle #7 : Syntaxe Correcte des Objets

Utiliser la syntaxe officielle PlantUML pour les objets avec attributs.

❌ Mauvais exemple (syntaxe incorrecte)

object "feat:" {
  Impact = MINOR
  Exemple = "3.0.2 → 3.1.0"
}

object "feat:" {
  Impact = MINOR
  Exemple = "3.0.2 → 3.1.0"
}
Pourquoi : Cette syntaxe n'est pas la syntaxe officielle pour définir les attributs d'un objet et peut causer des erreurs.

✅ Bon exemple (syntaxe correcte)

object feat
feat : Type = "feat:"
feat : Impact = MINOR
feat : Exemple = "3.0.2 → 3.1.0"

object feat
feat : Type = "feat:"
feat : Impact = MINOR
feat : Exemple = "3.0.2 → 3.1.0"
Pourquoi : C'est la syntaxe officielle de PlantUML pour les attributs d'objets, ce qui garantit un parsing correct.

Syntaxe officielle : 
object nomObjet
nomObjet : attribut1 = valeur1
nomObjet : attribut2 = valeur2

✅ Règle #8 : Éviter les Deux-Points dans les Noms d'Objets

NE JAMAIS utiliser : dans le nom d'un objet.

❌ Mauvais exemple

object "docs:" {
  Impact = Aucun
}

object "docs:" {
  Impact = Aucun
}
Pourquoi : Le : est réservé pour les séparateurs de stéréotype et d'attributs.

✅ Bon exemple

object docs {
  Type = "docs:"
  Impact = Aucun
}

object docs {
  Type = "docs:"
  Impact = Aucun
}
Pourquoi : Le nom de l'objet est un identifiant simple, et le type est défini comme un attribut, ce qui est la syntaxe correcte.

4. Diagrammes d'Activité

✅ Règle #9 : backward Uniquement dans repeat...repeat while

NE JAMAIS utiliser backward en dehors d'une structure repeat.

❌ Mauvais exemple (backward sans repeat)

if (Validation OK ?) then (✅ oui)
  :Continuer;
else (❌ non)
  :Corriger;
  backward :Re-tester;  # ❌ ERREUR
endif

if (Validation OK ?) then (✅ oui)
  :Continuer;
else (❌ non)
  :Corriger;
  backward :Re-tester;  # ❌ ERREUR
endif
Pourquoi : backward est un mot-clé réservé pour les boucles repeat.

✅ Bon exemple (repeat...repeat while)

repeat
  :Tests & validation;

  if (Validation OK ?) then (✅ oui)
  else (❌ non)
    :Corriger;
    :Rebuild;
  endif

repeat while (Validation OK ?) is (❌ non) not (✅ oui)

repeat
  :Tests & validation;

  if (Validation OK ?) then (✅ oui)
  else (❌ non)
    :Corriger;
    :Rebuild;
  endif

repeat while (Validation OK ?) is (❌ non) not (✅ oui)
Pourquoi : La structure repeat...repeat while est la manière correcte d'implémenter des boucles qui peuvent nécessiter de revenir en arrière.

5. Notes et Documentation

✅ Règle #11 : Utiliser des Notes pour les Contenus Complexes

TOUJOURS mettre les listes, le texte multiligne et les détails dans des notes.

❌ Mauvais exemple (Contenu dans le rectangle)

rectangle "Feature" {
  rectangle "Actions" {
    - Développer
    - Tester
    - Documenter
  }
}

rectangle "Feature" {
  rectangle "Actions" {
    - Développer
    - Tester
    - Documenter
  }
}
Pourquoi : Le parsing du contenu multiligne dans des nested rectangles est instable.

✅ Bon exemple (Contenu dans une note)

rectangle "Feature" #LIGHTBLUE as feature

note right of feature
  <b>Actions:</b>
  • Développer
  • Tester
  • Documenter
end note

rectangle "Feature" #LIGHTBLUE as feature

note right of feature
  <b>Actions:</b>
  • Développer
  • Tester
  • Documenter
end note
Pourquoi : Les notes sont conçues pour contenir du contenu riche et multiligne, garantissant un rendu correct.

✅ Règle #12 : Utiliser pour le Bold dans les Notes

Utiliser les balises HTML pour le formatage dans les notes. 

note right of element
  <b>Titre en Gras</b>
  <i>Texte en italique</i>
  <u>Texte souligné</u>

  Texte normal
end note

note right of element
  <b>Titre en Gras</b>
  <i>Texte en italique</i>
  <u>Texte souligné</u>

  Texte normal
end note
Balises supportées :
  • texte - gras
  • texte - italique
  • texte - souligné
  • texte - couleur

✅ Règle #13 : Échapper les Caractères Spéciaux dans les Notes

Utiliser < et > pour les chevrons dans les notes. 

note right of element
  Format: <source>2<dest>

  Fichiers:
  - commands/<name>.py
  - core/<name>_converter.py
end note

note right of element
  Format: <source>2<dest>

  Fichiers:
  - commands/<name>.py
  - core/<name>_converter.py
end note

✅ Règle #20 : Éviter les Caractères Spéciaux non Supportés

Éviter l'utilisation de symboles qui peuvent être interprétés comme des éléments PlantUML.

❌ Mauvais exemple (peut causer des problèmes de parsing)

rectangle "Ma Fonction => Resultat" {
  -- Option 1 --
}

rectangle "Ma Fonction => Resultat" {
  -- Option 1 --
}
Pourquoi : Certains symboles (comme =>, --, ->) ont une signification spéciale en PlantUML et peuvent perturber le parsing s'ils sont utilisés hors de leur contexte.

✅ Bon exemple (Utiliser des noms descriptifs sans symboles spéciaux ou notes)

rectangle "Ma Fonction et son Résultat" as funcResult

note bottom of funcResult
  Option 1 : Description
end note

rectangle "Ma Fonction et son Résultat" as funcResult

note bottom of funcResult
  Option 1 : Description
end note
Pourquoi : En évitant les symboles réservés, on garantit que le diagramme sera parsé correctement.

7. Diagrammes de Classes

✅ Règle #14 : Éviter les Class Diagrams si Graphviz n'est pas Installé

Les class diagrams avec relations (-->, -down->) nécessitent Graphviz.

❌ Mauvais exemple (NÉCESSITE GRAPHVIZ)

class "CommandA" {
  + main()
}

class "CoreA" {
  + process()
}

"CommandA" --> "CoreA" : utilise

class "CommandA" {
  + main()
}

class "CoreA" {
  + process()
}

"CommandA" --> "CoreA" : utilise
Pourquoi : Ce diagramme nécessite Graphviz pour le rendu, ce qui le rend moins portable.

✅ Bon exemple (FONCTIONNE SANS GRAPHVIZ - Utiliser rectangles)

rectangle "CommandA" #LIGHTBLUE as cmd
rectangle "CoreA" #LIGHTGREEN as core

cmd -down-> core : utilise

rectangle "CommandA" #LIGHTBLUE as cmd
rectangle "CoreA" #LIGHTGREEN as core

cmd -down-> core : utilise
Pourquoi : En utilisant des rectangles, le diagramme est compatible avec Slinky, le moteur de rendu natif de PlantUML, et ne nécessite pas d'installation de Graphviz.

Types de diagrammes nécessitant Graphviz :
  • Class diagrams avec relations
  • Component diagrams avec imbrication
  • Package diagrams
Types supportés par Slinky (sans Graphviz) :
  • Activity diagrams
  • Sequence diagrams
  • State diagrams
  • Object diagrams (sans relations complexes)
  • Mindmaps
  • Rectangles simples avec flèches

✅ Règle #15 : Simplifier les Class Diagrams en Rectangles

Convertir les class diagrams en rectangles + notes pour éviter Graphviz.

❌ Mauvais exemple (NÉCESSITE GRAPHVIZ)

class "commands/pdf2html.py" {
  + main(argv=None)
  + setup_parser()
  - process()
}

class "commands/pdf2html.py" {
  + main(argv=None)
  + setup_parser()
  - process()
}
Pourquoi : Ce diagramme de classe nécessite Graphviz.

✅ Bon exemple (SANS GRAPHVIZ)

rectangle "commands/pdf2html.py" #LIGHTBLUE as cmd

note right of cmd
  <b>Fonctions:</b>
  • main(argv=None)
  • setup_parser()
  • process()
end note

rectangle "commands/pdf2html.py" #LIGHTBLUE as cmd

note right of cmd
  <b>Fonctions:</b>
  • main(argv=None)
  • setup_parser()
  • process()
end note
Pourquoi : La conversion en rectangle avec une note est compatible Slinky et ne nécessite pas Graphviz.

7. Mindmaps

✅ Règle #16 : Pas de Markdown Bold (**) dans les Mindmaps

NE JAMAIS utiliser texte pour le bold dans les mindmaps.

❌ Mauvais exemple (** interprété comme niveau hiérarchique)

@startmindmap
* **Ambulon**
** CLI
*** Feature
@endmindmap

@startmindmap
* **Ambulon**
** CLI
*** Feature
@endmindmap
Pourquoi : * et définissent les niveaux hiérarchiques dans les mindmaps. L'utilisation de pour le gras est donc interprétée comme un niveau hiérarchique.

✅ Bon exemple (Pas de bold, ou utiliser )

@startmindmap
* Ambulon
** CLI
*** Feature
@endmindmap

@startmindmap
* Ambulon
** CLI
*** Feature
@endmindmap
Pourquoi : Pour mettre du texte en gras dans un mindmap, il faut utiliser les balises et ou ne pas en mettre du tout.

✅ Règle #17 : Respecter la Hiérarchie des Mindmaps

Structure hiérarchique stricte :
  • * - Nœud racine (1 seul)
  • ** - Niveau 1 (enfants de la racine)
  • * - Niveau 2 (petits-enfants)
  • ** - Niveau 3 (arrière-petits-enfants)

@startmindmap
* Racine
** Branche 1
*** Sous-branche 1.1
*** Sous-branche 1.2
** Branche 2
*** Sous-branche 2.1
@endmindmap

@startmindmap
* Racine
** Branche 1
*** Sous-branche 1.1
*** Sous-branche 1.2
** Branche 2
*** Sous-branche 2.1
@endmindmap

8. Compatibilité Slinky vs Graphviz

Comprendre les Deux Moteurs de Rendu PlantUML

PlantUML utilise deux moteurs de rendu :

1. Slinky (moteur natif Java) - Pas besoin de Graphviz - Activity diagrams - Sequence diagrams - State diagrams - Object diagrams simples - Mindmaps - Rectangles avec flèches simples

2. Graphviz (moteur externe) - Nécessite installation de Graphviz - Class diagrams avec relations - Component diagrams avec imbrication - Package diagrams - Deployment diagrams

✅ Règle #18 : Privilégier les Diagrammes Compatibles Slinky

Pour une portabilité maximale, utiliser les types de diagrammes qui fonctionnent sans Graphviz. Diagrammes recommandés (Slinky) :
  • Activity diagrams pour les workflows
  • Sequence diagrams pour les interactions
  • Rectangles simples pour les architectures
  • Object diagrams pour les données
  • Mindmaps pour les concepts
Diagrammes à éviter (Graphviz requis) :
  • Class diagrams avec relations -->
  • Component diagrams avec imbrication
  • Package diagrams

10. Checklist de Validation

Avant de Générer un PDF PlantUML

Vérifier les points suivants :
  • [ ] Pas de nesting > 2 niveaux de rectangles
  • [ ] Pas de listes à tirets dans des rectangles imbriqués
  • [ ] Pas de YAML/JSON indenté dans des rectangles
  • [ ] Tous les éléments ont des alias simples (pas de \n, :, etc.)
  • [ ] Notes utilisées pour les contenus complexes
  • [ ] Syntaxe object correcte : object nom puis nom : attr = val
  • [ ] Pas de : dans les noms d'objets ou rectangles
  • [ ] backward uniquement dans repeat...repeat while
  • [ ] Pas de dans les mindmaps** (sauf pour hiérarchie)
  • [ ] Class diagrams convertis en rectangles si pas de Graphviz
  • [ ] Utilisation de au lieu de ** pour le bold dans les notes
  • [ ] Commentaires utilisés pour documenter le code du diagramme
  • [ ] Pas de caractères spéciaux non supportés dans les noms d'éléments (ex: =>, --, ->)
